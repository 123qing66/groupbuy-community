# Git 使用与提交规范说明

> 对应评分项：「推荐使用 Git（GitHub / Gitee / 校内 GitLab）管理代码，主干 main + 功能分支 feature/xxx，每人保持稳定提交、commit message 说明改动内容。使用 Git 且有清晰提交记录的组可加分。」
> 本仓库：`https://github.com/123qing66/groupbuy-community`（GitHub），统计截至 2026-11-23。

## 一、分支策略：main + feature/xxx

采用 `main`（主干）+ `develop`（集成）+ `feature/xxx`（功能分支）+ `fix/xxx`（修复分支）的四层结构，所有功能通过 Pull Request 合入 `develop`，再统一发布到 `main`。

| 分支 | 用途 |
|---|---|
| `main` | 主干，稳定发布版本 |
| `develop` | 集成分支，各功能 PR 的合入目标 |
| `feature/activity-module` | 活动域 / 状态机 / 自提点 |
| `feature/order-seckill` | 下单抢购（限流 → Redis 预扣 → DB CAS） |
| `feature/order-status` | 订单状态机与支付回调 |
| `feature/stats-ranking` | 后台统计与排行 |
| `feature/excel-export` | Excel 导出 |
| `feature/demo-data` | 演示数据 |
| `feature/api-docs` | 接口文档与 HTTP 示例 |
| `feature/tests` / `feature/test-unittest` | 单元测试与集成测试 |
| `feature/perf-loadtest` | 压测脚本与报告 |
| `fix/cacheclient-jackson` | 缓存序列化修复 |

共 **13 个远端分支**，其中功能分支 10 个、修复分支 1 个，功能划分与成员分工一一对应。

## 二、提交记录清晰：规范格式占比 69%

`develop` 分支共 **56 个提交**（39 个开发提交 + 17 个 Merge 提交）。开发提交中 **27 个采用 Conventional Commits 规范**（`feat/fix/test/docs/chore/perf(scope): 说明`），合规率 69%。

规范示例（与评分标准给出的 `feat(order): 增加下单库存 CAS 校验` 同款）：

```
feat(order): 下单接口（时间校验→限购→限流）+ Redis预扣 + DB CAS兜底
feat(order): 模拟支付回调（验签+幂等+CAS）
feat(stats): 成团率统计（api.md 接口 13）
fix(redis): 缓存 Jackson 注册 JavaTimeModule，修复 LocalDateTime 序列化失败
test(activity): 补充活动域/自提点/绑定/核销码/缓存单测
perf: 200 并发下单压测脚本与实测报告（#27）
docs(api): 冻结接口契约v1.0（18条接口+错误码）
```

其余提交为仓库初始化阶段的基建提交（`Initial commit`、`Add CI workflow`、`Create PR template` 等），语义清晰但未套用前缀格式。
